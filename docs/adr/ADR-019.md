# ADR-019: Provenance contract v2

## Status

Accepted 2026-11-13 (plan S20). Implemented at plan S21, before the G2 clean run.
Amends the five provenance columns listed as an ingestion non-negotiable in the port spec.

## Context

Every landed row carries provenance columns set by `ingest/core/landing.py`: `_source`,
`_batch_id`, `_file_name`, `_ingested_at` and `_source_row_hash`. The row hash leaves them
out and covers everything else. A row's identity is therefore its source content, not the
run that carried it.

The plan S20 audit checked that contract against the landing bucket, as a test rather than a
reading of the code. It found four problems that a documentation edit cannot fix:

1. **Freshness is wrong for cached rows.** NPPES lookups are served from a cache with a
   30-day TTL (plan S16). A cached value carries the batch's `_ingested_at`, so a value
   observed 29 days ago looks as if it was read today. dbt source freshness at plan S23 would
   report stale data as fresh: a wrong answer, not a missing one.
2. **The leading underscore means two things.** The provenance columns are unhashed and set
   by landing. `_cms_release_year`, `_cms_dataset_uuid`, `_source_table` and `_raw_response`
   are hashed and set by sources. Nothing in a column's name says which kind it is.
3. **The row hash depends on the extractor's timezone.** `row_hash` serialises values that
   are not native JSON with `str()`. `str()` of an aware datetime keeps the offset it was
   built with. psycopg builds `timestamptz` values in the session `TimeZone`, so the same
   instant hashes differently under a different session setting.
4. **Test batches cannot be told apart from real ones.** Integration tests land into
   `landing/`, which is where the repeated copies of the 2023 release came from. Gate G2
   would undo itself: its idempotency test lands two more copies into the zone the clean
   run has just emptied.

The audit also found that `_file_name` held the part's file name rather than its object key.
That was fixed at S20 without a decision: the column is unhashed, and its documented meaning
was already "object key".

Timing makes now the moment to decide. Nothing reads the landing zone until plan S23, and S21
re-lands everything from zero. After S23, the hash changes below would make every row in the
history look modified at once.

## Decision

**1. A sixth provenance column, `_extracted_at`.** It records when the value was read from
its source.

- For anything read live during the run, it equals `_ingested_at`.
- It is earlier only when the value was served from a cache.
- Landing sets it by default. A source may supply it only when it knows better, which today
  means an NPPES cache hit carrying the entry's `fetched_at`.
- Contract: `_extracted_at <= _ingested_at` on every row.

**2. A naming rule for underscore columns.**

- Provenance columns are exactly `PROVENANCE_COLUMNS`, and the row hash leaves them out.
- Any other column beginning with an underscore is source metadata. It is included in the
  hash and carries its source's prefix: `_cms_`, `_nppes_` or `_pg_`.

Applied to the current columns:

- `_source_table` is dropped. Its value can be derived from `_source`. Because it is hashed,
  renaming a Postgres table would change every row's hash and make the entire history look
  modified. That makes it a latent trap, not just redundancy.
- `_raw_response` becomes `_nppes_raw_response`.

**3. Canonical hashing.** Before hashing, aware datetimes are converted to UTC and written as
ISO 8601. Dates are written as ISO 8601. Everything else is serialised as before.

**4. Test isolation.**

- Integration tests land under `landing_test/`, chosen through a `landing_root` setting.
- That prefix gets its own 7-day lifecycle rule, because the existing rule filters on
  `landing/`.
- The Snowflake storage role is scoped to `landing/` (plan S4), so the warehouse cannot see
  test batches by construction.

`tests/integration/test_provenance_contract.py` enforces all four against the bucket. It must
be green at G2.

## Rejected alternatives

**Keep five columns and document NPPES freshness as unknowable.** dbt freshness would still
give a wrong answer instead of declining to answer.

**An NPPES-only `_nppes_fetched_at`, left out of the hash by a per-source list.** This breaks
the rule that the hash excludes exactly the provenance columns. It would also give S23 a
freshness column for one source only.

**A documented list of underscore-column exceptions.** Every reader of a raw table would have
to consult the list to know what is hashed. A test can check a rule; a list can only be
remembered.

**Mark test batches with a column.** Readers find batches by globbing prefixes, so every
reader would have to remember a filter. A separate prefix needs nobody to remember anything.

**A separate test bucket.** It gives the same isolation for more Terraform and IAM than one
prefix and one lifecycle rule.

## Consequences

- Postgres and NPPES row hashes change once. That costs nothing, because S21 re-lands from
  zero.
- `_extracted_at` is the `loaded_at_field` for every source in `_sources.yml` at S23.
- Phase 4's raw table DDL carries six provenance columns.
- The lifecycle rule for `landing_test/` is part of this decision, not an optional extra.
  Without it, the prefix keeps every test batch forever.
- If CI runs integration tests at S50 under a role scoped by prefix, that role needs
  `landing_test/` as well.
