# ADR-014: GitHub Actions OIDC with immutable subject claims

## Status

Accepted 2026-10-30.

## Context

CI needs AWS access to read landed objects from S3. The two options are a
long-lived IAM access key stored as a GitHub secret, or OIDC federation in
which GitHub mints a short-lived token that AWS exchanges for temporary
credentials. ADR-011 already committed to eliminating long-lived credentials,
so OIDC was the only consistent choice.

The trust policy is the entire security boundary. Without a condition on the
`sub` claim, any GitHub repository anywhere could assume the role.

The initial policy used the subject format shown in GitHub's documentation,
AWS's documentation, and effectively every tutorial:

```
repo:<owner>/<repo>:ref:refs/heads/main
repo:<owner>/<repo>:pull_request
```

Four consecutive workflow runs failed with:

```
Not authorized to perform sts:AssumeRoleWithWebIdentity
```

Inspection of the AWS side showed nothing wrong. The OIDC provider existed
with the correct issuer URL and `sts.amazonaws.com` in its client ID list. The
role's trust policy named that provider, conditioned `aud` on
`sts.amazonaws.com`, and listed both expected `sub` values with the repository
owner and name spelled and cased correctly. Twenty-five minutes had passed
since creation, ruling out IAM eventual consistency. The error text named the
action but not the claim that failed to match, so it was equally consistent
with a wrong `sub`, a wrong `aud`, or a provider misconfiguration.

The only unexamined evidence was the token itself. A temporary workflow step
requested the OIDC token, decoded its payload and printed the claims, which
gave:

```
repo:LibertyKanojerera@35557707/pah-platform-snowflake-dbt-dagster@1384547718:ref:refs/heads/main
```

GitHub now appends immutable numeric identifiers to the owner and repository
names in the subject claim. The change shipped in April 2026 and rolled out to
newly created repositories first; this repository was created in September
2026 and so received the new format by default. Nothing in the configuration
was wrong. The format changed underneath documentation that has not caught up.

Reference: https://github.blog/changelog/2026-04-23-immutable-subject-claims-for-github-actions-oidc-tokens/

## Decision

**Pin the numeric owner and repository IDs in the trust policy, rather than
wildcarding them.**

```
repo:<owner>@<ownerID>/<repo>@<repoID>:ref:refs/heads/main
repo:<owner>@<ownerID>/<repo>@<repoID>:pull_request
```

The IDs are Terraform variables, and the subject string is assembled in a
local so the format appears once.

Two further scoping choices, unchanged by the above:

**Two specific contexts, not a repository wildcard.** `repo:...:*` would allow
any branch to assume the role, so an unreviewed feature branch could reach
production credentials. Only `main` and `pull_request` are trusted.

**`thumbprint_list = []`.** AWS no longer verifies thumbprints for OIDC
providers whose issuer uses a well-known CA, which includes GitHub, and
populated one itself on creation. Copying a thumbprint from a tutorial is how
these setups break silently when the certificate rotates.

## Rejected alternatives

**Wildcard the IDs**, as `repo:<owner>@*/<repo>@*:...`. Tolerates the format
without needing to know the values, and discards the entire benefit. A
repository name can be released by rename or deletion and re-registered by
someone else; a numeric ID is never reissued. Matching on the name alone means
trusting whoever holds that name in future.

**Accept both the old and new formats.** Would survive a revert of the
rollout, at the cost of leaving the name-only subject permanently trusted. The
failure mode of pinning is a loud, immediate CI failure that takes minutes to
fix. The failure mode of the permissive version is invisible.

**Store an IAM access key in GitHub secrets.** Contradicts ADR-011 three
sessions after making it, and is the thing OIDC exists to replace.

## Consequences

**The trust policy is coupled to this repository's identity.** Recreating the
repository, or transferring it to another owner, issues new IDs and CI stops
until the Terraform variables are updated. That is the intended behaviour: the
alternative is a policy that keeps trusting whatever now occupies the old
name.

**The security posture improved.** This presented as a breakage and is in fact
a hardening: the trust relationship is now anchored to identifiers that cannot
be recycled.

**Every tutorial on this subject is currently wrong.** Anyone following
published guidance on a repository created after the rollout will hit the same
opaque error. Worth stating in the migration write-up, because the lesson
generalises beyond OIDC.

**Methodological point, which is the part worth keeping.** The AWS side was
inspected repeatedly and was correct every time. Inspecting what you
configured cannot detect a change in what the other party sends; only the
transmitted value can. The claims dump answered in one run what three rounds
of policy inspection could not, and was then removed, having served its
purpose.

This is the same failure shape as ADR-010 at one remove. There, controls
reported success while operating on nothing. Here, a configuration was
verified correct against the wrong reference. In both cases the resolution was
to observe the actual value rather than the intended one.

A second instance arrived in the same session and belongs with ADR-010: once
OIDC worked, the smoke step still failed, because `aws s3 ls` exits 1 on an
empty listing and so could not distinguish "no objects" from "no access". It
was replaced with `aws s3api list-objects-v2`, which exits 0 when empty and
fails loudly on `AccessDenied`. A verification step that cannot tell success
from absence is not a verification step.
